# plan-feature

## 목적
모호하거나 큰 요청을 바로 구현하지 않고, 구현 가능한 단위로 정리한다.

## 사용 시점
- 요구사항이 추상적일 때
- 정책·흐름·계약이 불명확할 때
- 개발 전 범위 정리가 필요할 때

## 모호할 때 grilling (절차 1 직전)

1. **도구·코드베이스로 알 수 있는 것은 사람에게 묻지 않는다.**
2. **한 라운드에 확인 질문 1~2개**만 한다(스택, 루트 구조, 핵심 계약, 인증, 도메인 모델, 권한 등).
3. 답 전에는 **구현하지 않고** 초안에서 **확정처럼 단정하지 않는다.**
4. 답하지 않으면 **미확정**으로 남긴다.

## 절차
1. 요청의 목표를 정리한다.
2. 사용자 유형과 사용 시나리오를 정리한다.
3. 핵심 기능과 선택 기능을 나눈다.
4. 미확정 항목과 가정을 구분한다.
5. API가 포함되면 계약 초안 범위를 적는다.
6. 필요하면 `prd-agent`로 문서화한다.
7. PRD에 **수용 기준(AC)** 섹션을 포함한다. [`docs/qa/acceptance-criteria.template.md`](../../../docs/qa/acceptance-criteria.template.md), [`docs/qa/atdd-lite.md`](../../../docs/qa/atdd-lite.md)
8. `.cursor/rules/60-delivery-gates.mdc` Gate 1에 맞는지 점검한다.
9. 이후 `start-feature` 또는 Gate 2 충족 시 `parallel-delivery`로 넘길 수 있게 정리한다.

## 결과물
- 기능 범위 정리
- 가정/미확정 목록
- Gate 1 점검 메모

## 예외
- 요청이 이미 충분히 구체적이면 생략 가능.
